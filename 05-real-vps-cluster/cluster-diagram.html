3-VPS k3s Cluster — how the pieces connect

One control-plane server, two worker agents, each a fully separate real machine

Control plane (server VPS only) Data plane (every VPS) Pod network overlay (flannel / UDP 8472) Terraform bootstrap (SSH, one-time)

What Terraform actually does (the purple dashed lines): it SSHes into VPS 1 once to install k3s as the server, reads back the join token over another SSH call, then SSHes into VPS 2 and VPS 3 to install k3s as agents pointed at VPS 1's private IP. After that, Terraform's job is finished — those connections aren't used again unless you re-run apply.

What keeps running afterward (blue, green, gold): the control plane on VPS 1 continuously makes decisions (what to schedule, where, whether anything needs restarting) via its own reconciliation loop — this is the part that keeps running independently of Terraform, forever, until you turn it off. Each VPS's kubelet manages whatever pods got assigned to it, and the flannel overlay network is what lets a pod on VPS 2 talk to a pod on VPS 3 by IP as if they were on the same LAN, even though they're two separate physical machines possibly in different racks or data centers.

Firewall reminder: ports 6443 (API server), 10250 (kubelet), and UDP 8472 (flannel) need to be open between these three VPS specifically — not to the whole internet. That's what the earlier practice stage's "iptables FORWARD DROP" problem was really teaching, just inside a fake LXD network instead of a real firewall.
